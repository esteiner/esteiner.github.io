  Answering your question directly — "why isn't the sync checking last-modified 
  first?"

  I traced the sync from SolidSyncService.synchronize() into the soukai-bis Sync
  job and verified behavior against the live CSS. The short answer: the 
  per-document last-modified check exists, but Kellermeister never gets a 
  whole-container short-circuit, and the per-document skip under-fires.

  Concretely:

  1. The container listing already carries what's needed. A single GET on
  bottles/ returns dc:modified for every child — I confirmed CSS 7.2.0 emits
  this (<child> dc:modified "…" per resource). bis parses each child's updatedAt
  from that one response, so no extra request is needed to know what changed.
  2. No whole-container gate. Sync can only skip an unchanged container subtree
  via extra:deepLastModified, which stock CSS does not emit. Kellermeister also
  registers the four leaf collection containers directly as pull roots
  (buildTypeIndex), seeded with no expected date — so every sync reads all four
  containers in full regardless.
  3. The per-child skip's local baseline is unreliable. Sync.skipDocumentPull
  compares the Pod's dc:modified to the locally stored lastModifiedAt. That
  local value is missing for local-first docs, cleared to undefined by every 
  ordinary edit (IndexedDBEngine.updateDocument, line ~169), and set from
  second-precision HTTP Last-Modified/estimated push timestamps that drift
  outside the 1 s tolerance. Whenever it doesn't match, the document is GET'd
  individually — so a ~840-bottle Pod pulls hundreds of documents even when
  little changed.

  The proposed fix persists the Pod's dc:modified (ms precision) as the local
  baseline right after each pull/push so the skip becomes an exact match, plus a
  container-level gate driven by the child dates already in the listing. I also
  confirmed the re-home step (MigrateLocalUrls) is local-only and not a source
  of Pod requests.

  One thing I flagged as an open question rather than assuming: whether CSS
  bumps a container's own dc:modified on in-place child edits (vs. only
  add/remove). The design deliberately doesn't depend on that — it uses the
  per-child dates from the listing — but confirming it (task 1.3) would allow an
  even cheaper first gate.

  resolve the open questions first.

● Confirmed. The purl: prefix expands to http://purl.org/dc/terms/, so the field
  the skip depends on is dcterms:modified.

  The prerequisite

  The Pod server must include dcterms:modified 
  (http://purl.org/dc/terms/modified) for each contained resource in its LDP 
  container listing (the response to a GET on a container).

  That single property is what the whole optimization hinges on.

  Why — the mechanism

  soukai-bis Sync pulls a collection like this:

  1. GET {base}bottles/ → parses the container listing into child Resources.
  Each child's updatedAt comes from dcterms:modified in that listing
  (Resource.schema.ts: updatedAt: rdfProperty(date(), 'purl:modified')).
  2. For each child it calls skipDocumentPull(url, remoteUpdatedAt), comparing
  that dcterms:modified against the locally stored lastModifiedAt.

  The skip's very first guard is:

  if (!remoteUpdatedAt || !lastModifiedAt) return false;  // → fetch the 
  document

  So if the container listing has no per-child dcterms:modified, remoteUpdatedAt
  is undefined for every child → skipDocumentPull returns false for all of them
  → every document is fetched individually. That's your ~2000 requests, and no
  amount of correct local state helps — the client has nothing to compare
  against.

  CSS emits these by default (verified: a container GET returns <child> 
  dc:modified "…"^^xsd:dateTime per member). Many other implementations only
  emit ldp:contains <child> and omit per-child metadata — which is spec-legal,
  but defeats this optimization.

  How to check a given server

  GET one of your collection containers as Turtle (authenticated) and look at
  what's attached to each child, e.g.:

  curl -H "Accept: text/turtle" -H "Authorization: …" \
    https://your-pod/private/kellermeister/v1/bottles/

  - Works: each <uuid> child has a dc:modified "…"^^xsd:dateTime triple
  (alongside ldp:contains).
  - Won't work: the container only lists ldp:contains <uuid>, <uuid>, … with no
  dc:modified per child → every sync re-fetches everything.

  (Note: the container's own dc:modified and posix:mtime are not enough — it
  must be per child. And the value must be stable across GETs, reflecting the
  resource's real mtime; sub-second precision differences are absorbed by Sync's
  1000 ms tolerance.)

  If a server doesn't expose it

  There's no client-side workaround inside bis Sync — the property has to come
  from the server. Options, roughly in order of preference:

  1. Configure/patch the server to include resource modified-dates in container
  listings, if it supports that.
  2. Use a server that does (CSS does out of the box; check ESS/Inrupt and NSS
  configs).
  3. Add a client-side incremental layer outside bis — e.g. per-document
  conditional HEAD/GET with If-Modified-Since (still N requests, but cheap 304s
  instead of full bodies), or a maintained manifest/change-log resource on the
  Pod. This is real custom work, not a config flag.
  4. Accept the full pull on those servers.

  One thing that is not required: the nested-container short-circuit uses a
  separate, non-standard extra:deepLastModified predicate — but CSS doesn't emit
  that either, and Kellermeister's flat one-level collections don't rely on it.
  The only hard requirement is per-child dcterms:modified.

  If you tell me which server implementation you're hitting the 2000 requests
  on, I can check whether it can be configured to include per-child modified
  dates.

❯ Could we implement the client-side incremental layer outside bis only as a    
  fallback in case the used Pod server doesn't provide the necessary            
  dc:modified triple?                                                           

● Yes — and it's a clean design because the decision can be made from a one-time
  capability probe at the start of a sync, with the native (bis) path
  completely unchanged when the server behaves.

  The shape

  Probe (cheap, you already pay for it): the first container GET of a sync tells
  you everything — parse the listing and check whether children carry
  dcterms:modified. If yes → native path (today's behaviour). If no → fallback
  path. One boolean, cached per session per Pod.

  The elegant integration for the fallback: instead of reimplementing bis Sync's
  pull (the thing the migration deliberately removed), wrap the remote
  SolidEngine in a decorator that synthesizes the missing dcterms:modified. When
  it reads a container, it fills in each child's dc:modified from that
  resource's HTTP Last-Modified header (via a HEAD), then returns the augmented
  container document. bis Sync.skipDocumentPull then works identically to the
  CSS case — you change nothing in Sync, and the whole optimization "just works"
  on the fallback path too.

  synchronize():
    hasDcModified = probe(container)          // 1 request, cached
    remoteEngine = hasDcModified
        ? new SolidEngine(...)                 // native — unchanged
        : new LastModifiedAugmentingEngine(...) // fallback — HEAD-fills
  dc:modified
    Sync.run({ ..., remoteEngine })            // same call either way

  The honest limits

  - It's still O(N) round-trips on the fallback path — one HEAD per child to
  learn its Last-Modified. That takes your ~2000 heavy GETs (bodies + operation
  docs + merges) down to ~840 light HEADs + full GETs only for the
  genuinely-changed docs. A big win in bandwidth and time, but not O(changes) —
  you can't get below one probe-per-resource without the server putting the info
  in the listing.
  - It requires the server to return a stable per-resource Last-Modified header.
  Almost all do (it's plain HTTP), but it must be confirmed — it's a different
  guarantee than the dc:modified triple.
  - Precision & the push caveat: HTTP Last-Modified is second-precision; bis's
  1000 ms tolerance absorbs that. Pushed-then-not-re-fetched docs could hit the
  same estimate drift we fixed for the well-known cellars — the same
  reconciliation trick would apply.

  Cheaper-but-worse alternatives (for completeness)

  - ldp:contains membership diff: compare the listing's member set to a local
  snapshot → detect adds/removes in O(1) requests. Cheap, but misses in-place 
  edits (a child whose content changed without membership changing). Only safe
  for an append-only workload.
  - A manifest/change-log resource on the Pod: gives true O(changes) requests,
  but every writer must update it atomically → contention and cross-device race
  complexity. Fragile; I'd avoid it.

  My recommendation

  1. First confirm the premise — run the curl on an iGrant container and check
  for per-child dc:modified. Don't build a fallback for an unconfirmed cause;
  iGrant may be configurable server-side, which is by far the cheapest fix.
  2. If it's genuinely absent, build the probe + LastModifiedAugmentingEngine 
  decorator. It's contained (one engine class + one probe), reuses bis Sync
  untouched, is correct for edits, and degrades gracefully (if Last-Modified is
  also missing, fall back to full pull).

  capability check? If so, paste an iGrant container listing first so I can
  confirm both what's missing (dc:modified) and what's available (Last-Modified
  on HEAD) before writing code.
